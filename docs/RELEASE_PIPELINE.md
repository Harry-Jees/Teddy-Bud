# Release and Android APK pipeline

## Source of truth

- Platform packages are generated by the **CI and platform builds** workflow.
- Pull requests run client and gateway checks only. They do not publish packages.
- A push to `main` runs the client checks, gateway tests, Android build, and desktop packaging.
- The distribution collector downloads artifacts from that same workflow run, assembles the complete package set, and runs `scripts/verify_distributions.py`.
- The release workflow accepts only a successful CI run from this repository's current `main` commit. It does not accept caller-supplied run IDs or artifacts from other workflows.

## Android APK checks

The Android job builds the ARM64 release variant and verifies:

1. The APK exists and is non-empty.
2. Android's `apksigner` accepts the APK signature.
3. `zipalign` reports correct alignment.
4. The manifest package ID is `com.teddybud`.
5. The APK checksum is recorded in the job log and in the release SHA-256 manifest.

These checks establish package integrity and signing validity; they do not replace installation and runtime testing on a physical Android device.

## Signing note

When `ANDROID_KEYSTORE_FILE` is not configured, Gradle signs the test APK with the CI debug key. That makes the APK installable, but the runner-generated debug certificate is not a stable update identity. A stable production update path requires a dedicated release keystore and the corresponding GitHub Actions secrets:

- `ANDROID_KEYSTORE_FILE`
- `ANDROID_KEYSTORE_PASSWORD`
- `ANDROID_KEY_ALIAS`
- `ANDROID_KEY_PASSWORD`

Never commit the keystore or its passwords to the repository.

## Release publication

After package verification, the release workflow recreates the `v1.0.0` release against the exact source commit that produced the packages and attaches the APK, desktop installers, and `SHA256SUMS.txt`. Recreating the release refreshes its GitHub publication date; simply replacing assets on an existing release does not change its original publication date.

Generated files under `dist/` remain ignored by Git and are published as workflow artifacts and GitHub Release assets, not committed to source control.
